## How to work (owner, repeated on Oct 25; follow it exactly)
- **Ask, don't assume.** When a rule, scope or wording decision belongs to the owner, ask with options and a
  recommendation (AskUserQuestion). Never change who, when or how much (rules, money, policy) on your own. Push back with
  research when something is overdone.
- **Be as thorough in testing as the Oct 25 session was. The owner called this out explicitly:**
  - Run the full suites, not just the focused ones:
    - client: `npx vitest run`;
    - server: `npx vitest run -c vitest.config.server.ts`;
    - then `npx tsc --noEmit -p .`.
    The default vitest config **excludes `server/**`**, so a server test named on the default command silently doesn't
    run.
  - Run the suites **one after another, not in parallel**. Parallel runs starve CPU and make slow tests time out.
  - **Never call a failure "pre-existing" or "flaky" without proof.** Rerun it alone and read the actual error. Find the
    cause and fix it there:
    - a stale expectation gets fixed in the test, after you confirm the code is right;
    - a slow test gets made faster (profile it step by step);
    - a real bug gets fixed in the code.
    Don't raise timeouts as a band-aid. Oct 25 brought the whole suite green this way (see the log).
  - Each new migration runs for real in a test (PGlite; `@electric-sql/pglite`, plus `drizzle-orm/pglite` when service
    code needs it) and twice to prove it's idempotent. Then apply it to dev with
    `node .phase0-harness/apply-migration.mjs <file>` before pushing code that needs it.
  - The `*.postgres.check.ts` files require a disposable Postgres. Never point them at the shared dev DB; use a PGlite
    test instead.
  - Drive the real flow, not just tests. Locally first (`chef.localhost:5002`), then live on dev after the deploy, on
    desktop (1440×900) and phone (iPhone 13). Look at the screenshots yourself: menus, dialogs, empty, error and success
    states, and both sides (chef and kitchen) for anything that notifies the other side. Report the visual check and the
    test results separately.
- **Skills:**
  - UI: taste-skill for the base, then impeccable to refine.
  - Customer copy: no-ai-slop.
  - Payments and auth: vibe-security.
  - Chat with the owner: caveman voice. Code: ponytail (smallest complete change; fix callers, tests and fixtures too).
- **Batch deploys:** commit only your files (never `graphify-out/`, `.workbuddy-ai/`, `outputs/`, `.verify*`). Push to
  `development`, watch `gh api repos/:owner/:repo/commits/<sha>/status` in the background, then check the change live on
  dev.
- **Log every batch** in `PHASE0_LOG.md`: owner decisions, built, bugs found, verified, open items.
- The owner sends "not trying to interrupt" notes mid-task. Finish the current item, then handle the note; keep a list
  so none get lost.

## Harness
- **Local server.** Start it yourself in the background: `PORT=5002 npm run dev > .phase0-harness/dev-5002.log 2>&1`.
  - Restart it after server code changes; there's no watch mode for the server.
  - Only stop processes you started. Port 5001 may belong to another session.
- **Hosts:** local `chef.localhost:5002` and `kitchen.localhost:5002`; dev `dev-chef.localcooks.ca`.
- **Walks:**
  - `node .phase0-harness/chef-walk.mjs <email> <outdir> "login,go:/path,wait:ms,click:Name,tid:testid,loc:css,fill:sel=val,check,tall,scroll:y,shot:tag" [--mobile]`.
    Steps are **comma**-separated. Set `CHEF_BASE=https://dev-chef.localcooks.ca` for dev.
  - Signed-out walks use `guest-walk.mjs`.
- **Accounts:**
  - Fresh chefs: `make-test-chef.cjs <email> <base> [--no-terms]` (`TEST_NAME` env sets the name), then
    `verify-email.cjs <email>`.
  - Synthetic logins: phase0-chef (380: approved at location 47 / kitchen 54, in review at location 46 / kitchen 53),
    phase0-manager (379), phase0-admin (381).
  - Passwords via `set-pw.cjs`. The owner's own account raunaksarmacharya9 may be used.
- **i18n keys:** `node .phase0-harness/addkeys.cjs spec.json`, where the spec is shaped `{ns:{key:[en,fr,uk]}}`.
- **Editing:** use the Edit or Write tools for anything with regex or `\n`. Python and sed heredocs mangle backslashes;
  this happened twice on Oct 25.
- **Dev DB** is shared with deployed dev (Supabase `zjiaghzmmgvswsllzxip`). Don't edit shared rows casually. Use
  `date_trunc('milliseconds')` when moving times.
