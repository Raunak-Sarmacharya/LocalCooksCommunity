# Arrival communication: research and UX decision

Research checked **2026-10-13**. Design recommendation only; no source, database, migration, outbound message or git-state changes. The visit-code proposal, server/client checkpoints and relevant PHASE0_LOG sections were read. Current source takes precedence over historical checkpoints; implementation packages below are future work.

## Decision

**Tell chefs how arrival works at confirmation; explain it in the preparation reminder; repeat one action line shortly before arrival. Keep the staffed visit code with staff until the chef arrives.** The authenticated visit page is the current source of instructions and mode. Call the modes **“Meet kitchen staff”** and **“Self check-in”**. A visit code confirms the staff handoff; a door code opens a building. Never use either label for the other.

The owner's preparation-email hunch is supported, but no researched platform establishes a universal T−24h rule. Airbnb generally releases its detailed arrival guide at T−48h; Vrbo emails its welcome guide at T−72h; Peerspace and LiquidSpace provide access guidance with confirmation. Keep Local Cooks' existing configurable defaults: preparation 24h, arrival 2h, departure 30min, session-ending 15min.

**Repository correction:** preparation is not currently the first possible exposure of instructions. `BookingPreparation` displays them on confirmed bookings, `generateBookingConfirmationEmail` can include them, and the lifecycle producer supplies them. No hard T−24h release gate exists there. Preserve early access to useful guidance; do not invent a new withholding gate for ordinary instructions.

## 2. Communication timeline and ready-to-use copy

All times refer to **each visit's kitchen-local scheduled start**, using saved instants and the location timezone. Every notice includes kitchen/location, visit date/start/end/zone and reference. Never rely on “tomorrow” alone. Email and in-app notices share the same brief copy; page content supplies detail. In-app notification means the existing notification inbox, not an unimplemented native push/SMS promise.

Chef CTA: **“Open your visit”** → `/booking/{bookingId}/visit?visitId={visitId}` for split visits, `/booking/{bookingId}/visit` for single visits. Manager CTA: **“Prepare for arrival”** → `/manager/booking/{bookingId}#visit-code-{target}` (proposed target anchor). Confirmation keeps the full booking/calendar CTA as well.

### At-door recovery copy

- Wrong code: **“That visit code doesn't match. Check the current code with kitchen staff and try again.”** Show attempts remaining after rejection. Keep tasks/photos/notes while the form stays open; do not promise reload/offline persistence. Never suggest guessing.
- Five wrong attempts: **“Ask kitchen staff for a new visit code. Too many incorrect attempts have paused arrival confirmation.”** Buttons **“Message kitchen”**, **“Get help from Local Cooks”**. Manager can rotate or use the existing audited assisted-arrival flow; no code needed for assistance, but evidence/status/window rules still apply.
- Staff absent / cannot get inside: **“Can't get inside or find staff? Contact the kitchen. Don't confirm arrival until you're at the kitchen.”** Offer kitchen call when a number exists, otherwise message/email, plus **“Report an access problem”** and Local Cooks contact. No automatic switch to SELF; no no-show inference from a blocked/missing tap.
- Network failure: **“Arrival hasn't been confirmed yet. Your details are kept while this page stays open. Try again when you're connected, or ask the kitchen to record your arrival.”** A submitted but unknown result first refreshes status; retry the same operation without duplicate arrival.
- Code rotated / mode changed: **“Arrival details changed. Review the current instructions.”** Clear only stale code/error state; retain required evidence drafts. If cancelled, show cancellation, disable submission and retain support/history access.
- Before/after eligibility: show the saved kitchen-local opening/closing time, reason and assistance link. In-session and departure reminders never ask for the arrival code again.

Support copy must use the actual service hours. The current in-session UI says Mon–Fri 9am–5pm Newfoundland time, after-hours reply within 24h; this is repository copy, not verification of staffing. Do not promise 24/7 instant rescue. The kitchen needs a reachable day-of fallback, especially for SELF.

## 3. Credential policy and security reasoning

**STAFFED attendance code: chef sees it only when staff gives it on arrival.** Staff may read it in the authenticated owned visit card beforehand. The chef API exposes mode/state, never digits. Sending digits to the chef earlier would let them satisfy the code condition without the intended handoff. A code still is not independent physical-presence proof; don't promise fraud-proof attendance.

**SELF attendance: no credential to copy.** The authenticated booked chef confirms arrival with the required evidence; manager-enabled mode is recorded distinctly. Neither an early app tap nor a door code proves arrival.

**Building access credential: separate policy and data.** If Local Cooks later stores a per-visit door/lockbox code, show it to the authorized chef on the authenticated visit page at T−24h (immediately for a later confirmation), clearly labelled **“Door code”**, with actual validity times and backup contact. If a lock can enforce time limits, activation is at the agreed access time; Local Cooks must not claim it controls a manual lock. For reusable/manual codes, use a deliberate manager handoff and rotation process until secure per-visit access exists; no automatic pre-release of a building-wide secret.

Keep **no code in system-generated email or notifications** for this release. Research provides a real counterexample—Airbnb emails time-scoped door codes—but it does not outweigh the staffed attendance purpose or Local Cooks' lack of integrated lock activation/revocation. A visit-code cancellation revokes app attendance eligibility; it does **not** revoke a physical door credential. Manager must remove/rotate external access separately. Email already delivered cannot be recalled.

Current privacy gap: confirmation, preparation and instruction-update emails interpolate arbitrary instructions; `generateChatMessageEmail` also includes a preview. A manager typing a door code there could put it in email. Until instruction text has a reliable safe/secret separation, email uses useful **platform-authored mode guidance + dates/address/contact + authenticated instruction link**, with no arbitrary access-instruction body/diff or booking-chat preview. Do not attempt to recognize secrets with a “strip six digits” regex. Keep the full instructions in the authorized page; warn managers not to place credentials in general notes/listings. Existing digests are already link/count based. This is a proposed privacy correction, not a claim that today's emails cannot leak manually entered secrets.

## 5. OWNER QUESTIONS — only unresolved product forks

1. **Should SELF activation require usable entrance/access instructions and a reachable kitchen contact, or only warn?** Recommend **block when missing**; instructions must explain how to get in without staff. A reason like “manager away” is insufficient. Do not require a door code when none is needed. Existing publication checks help but cannot prove this visit is actually ready for unattended access.
2. **Should SELF→STAFFED switches be blocked inside T−2h, or allowed with staff coverage and direct coordination?** Recommend **allow with explicit staff-coverage confirmation and a direct-contact warning**; a blanket freeze prevents recovery. Email/in-app notices alone are insufficient. Acknowledgement/consent workflow would be a larger separate policy feature; do not pretend a queued notice supplies it.
3. **Should this release store/reveal physical door credentials, or keep that a separate access feature?** Recommend **separate feature**. Ship the attendance communication now, with clear non-secret entry instructions and manager-provided secure access arrangements. If managed door codes are needed now, design separate permissioned storage, timed reveal, external revocation and offline fallback before offering automated code display. Keep codes out of email either way.

Already settled; do not reopen: six digits/five failed attempts, staffed default, deliberate per-visit/all-open-visits SELF, manager-assisted arrival without a code, new-confirmation enrollment, and arrival evidence independent of billing/settlement.
