### Why the serverless loader fails; what its fallback actually does

The warning originates at **`server/email.ts:72`**. An unawaited module-start IIFE starts with the fallback already installed (`server/email.ts:33`, `server/email.ts:37`), derives a directory from `import.meta.url`, then dynamically imports five filesystem URLs (`server/email.ts:43`, `server/email.ts:48`, `server/email.ts:59`). Every exception is swallowed (`server/email.ts:66`). Even a successful asynchronous load could leave an early call using the fallback.

The Vercel build emits **one bundled `api/index.js`**, directly from TypeScript with esbuild; it does not emit a separate `shared/timezone-utils.js` or `api/shared/timezone-utils.js` (`vercel-build.mjs:31`, `vercel-build.mjs:48`). The explicit shared-file copy is search JSON (`vercel-build.mjs:49`). Vercel invokes that production script (`package.json:10`, `vercel.json:3`), and function extra files cover `server/assets/**` (`vercel.json:13`). The loader's comment assumes an obsolete `server/email.js` + separate shared JS layout (`server/email.ts:47`).

In the checked-in bundle, the shared helper is already inlined (`api/index.js:4349`, `api/index.js:4443`), yet the variable `import(timezoneUtilsUrl)` survives (`api/index.js:13878`, `api/index.js:13894`). Its `import.meta.url` now identifies `api/index.js`: the relative probes target a separate shared JS file outside that bundle; the absolute probes also target files the build never emits. An extensionless probe cannot substitute for an uncompiled `.ts` source file. This build/layout mismatch explains the supplied warning; the exact deployed exception cannot be identified because exceptions are discarded, and deployed package contents were not inspected.

**The current fallback is not fixed-offset, UTC-wall-clock or server-local arithmetic.** It calls `matchingLocalInstants(date, time, suppliedIanaZone)[0]`, rejects gaps and picks the first occurrence in a fold (`server/email.ts:26`, `shared/booking-dst.ts:19`). Its omitted-zone default is hardcoded Newfoundland (`server/email.ts:26`, `server/email.ts:79`). Compared with canonical TZDate: ordinary winter/summer conversions agree; gaps throw instead of normalizing; ambiguous times select the earliest candidate instead of requesting disambiguation. The warning is a brittle-loading defect, not evidence of a current fixed −03:30 fallback.

Its scope is **email calendar construction**, including calendar links and grouped-slot ICS (`server/email.ts:762`, `server/email.ts:882`), called by request and confirmation generators (`server/email.ts:3541`, `server/email.ts:3843`, `server/email.ts:3881`; old status generator at `server/email.ts:3739`). It does not replace route/service cancellation, availability, check-in or reminder helpers. Request generators compute calendar-derived labels but do not attach a confirmed invite (`server/email.ts:3543`, `server/email.ts:3845`).

| Gaps/folds/overnight | Canonical and fallback differ on gaps; neither conversion alone demands explicit fold choice (`shared/timezone-utils.ts:44`, `server/email.ts:27`). Tours' input does (`shared/tour-visit-input.ts:15`). Generic `isBookingActive` assumes start/end share one date (`shared/timezone-utils.ts:69`, `client/src/utils/timezone-utils.ts:108`); overnight callers need operating-day resolution, as existing calendar utilities support (`shared/booking-dst.ts:1`). |

### Recommended modular standard

1. **One statically imported shared conversion/formatting API**, using existing `@date-fns/tz` and `matchingLocalInstants`; remove filesystem probing and browser offset guessing. Reuse tour scheduling/input algorithms, parameterizing their current DEFAULT policy (`shared/tour-schedule.ts:31`, `shared/tour-visit-input.ts:11`, `shared/tour-time.ts:3`). Reject gaps; make fold choice explicit or consistently forbid ambiguous hourly slots.
2. Require/validate an IANA zone per location; keep Newfoundland only as an onboarding default. Remove manager/UI locks. Snapshot the agreed zone on the booking/visit alongside operating date and wall-clock schedule, because current schema lacks it (`shared/schema.ts:547`, `server/routes/manager.ts:5481`). Derive scheduled **UTC start/end instants**, persist as PostgreSQL `timestamptz`; keep operating-day keys as dates, not fake midnight instants. Store actual actions as instants. Carefully backfill existing timestamp-without-zone fields after verifying their historical interpretation; do not blindly convert (`shared/schema.ts:2338`, `shared/schema.ts:644`).
3. Define policies explicitly: elapsed-hour notice/cancellation windows subtract epoch duration; local midnight/calendar-day cutoffs use zoned calendar construction. Preserve frozen-zone overstay calendar logic (`server/services/overstay-penalty-service.ts:186`) and tour midnight pattern (`shared/tour-reschedule.ts:6`). Use one per-visit start/end resolver including overnight operating windows.
4. Pass the same zone/instant DTO to availability, checkout, claims, reminders, UI and emails. Format with `Intl.DateTimeFormat({timeZone, ...})` against the actual instant; show human zone + seasonal abbreviation/offset and IANA identifier. Avoid a fixed GMT−3:30 label and host-local reconstruction (`shared/timezone-utils.ts:110`, `shared/timezone-utils.ts:145`). ICS should use agreed UTC instants and stable identity; frontend/browser timezone should not change policy.

## 3. Lifecycle timing, duplicates and recipient defects

1. **Cancellation request emailed as completed cancellation.** Confirmed standalone storage is saved as `cancellation_requested`, then helper sends both chef/manager generators with “Booking Cancelled” subject/badge (`server/routes/bookings.ts:463`, `server/routes/bookings.ts:479`, `server/routes/bookings.ts:566`, `server/routes/bookings.ts:581`, `server/email.ts:3645`, `server/email.ts:4008`, `server/email.ts:4035`). A “reason” mentioning request does not fix the dominant state claim. Emit request receipts/manager review CTA; cancelled receipt only after committed acceptance.

2. **Authorization emailed as payment received/paid.** Storage extension completed webhook records manual-capture payment as authorized (`server/routes/webhooks.ts:1529`) but unconditionally calls payment-received template (`server/routes/webhooks.ts:1703`), whose content says received and Amount Paid (`server/email.ts:4521`, `server/email.ts:4526`). Split authorized/captured copy based on recorded provider status; do not send capture receipt at authorization.

3. **Two storage-extension approval/rejection emails.** Both rich and inline sends execute for the normal same chef (`server/routes/manager.ts:6877`, `server/routes/manager.ts:6915`, `server/routes/manager.ts:7209`, `server/routes/manager.ts:7243`). Second rejection also promises refund even after refund error is caught or when authorization was released (`server/routes/manager.ts:7189`, `server/routes/manager.ts:7250`). Replace each decision with one durable event/template; financial receipt is separate and only based on verified evidence.

4. **Delayed first confirmation can carry an obsolete active invite.** Normal booking delivery only reads current status on replay/recovery (`server/services/booking-lifecycle-delivery.ts:129`, `server/services/booking-lifecycle-delivery.ts:132`). A confirmed event queued before a later cancellation/completion can therefore still be sent as active confirmation on its first delayed delivery. Historical ICS removal is guarded by that historical flag (`server/services/booking-lifecycle-delivery.ts:169`, `server/services/booking-lifecycle-delivery.ts:178`). Tours validate current status/facts/recipients on ordinary dispatch (`server/services/tour-delivery-service.ts:722`). Apply that discipline to every booking delivery, not just recovery.

5. **Notification inbox ignored by modern booking outbox.** Normal request/confirmation/cancellation selects M's login email, not N (`server/services/booking-lifecycle-delivery.ts:21`, `server/services/booking-lifecycle-delivery.ts:25`), while legacy webhook/portal, extension and detection use N with inconsistent fallbacks (`server/routes/webhooks.ts:1085`, `server/routes/portal.ts:489`, `server/routes/webhooks.ts:1689`, `server/services/outcome-delivery.ts:270`). Configured operations inbox can miss booking notices, contrary to mailbox setup email (`server/email.ts:4414`). Tour also deliberately uses M (`server/services/tour-delivery-service.ts:77`), so copying tour recipients does not resolve this. Define whether N replaces/copies M, then enforce centrally with current assignment/address revalidation. Only change-event booking delivery currently rechecks snapshot recipient authority/address (`server/services/booking-lifecycle-delivery.ts:158`).

6. **Initial payment-failure email absent.** `payment_intent.payment_failed` updates transaction to failed and creates manager in-app notification (`server/routes/webhooks.ts:2150`, `server/routes/webhooks.ts:2259`). Financial email queue only handles failed after succeeded/partially-refunded, not initial pending/authorized failure (`server/services/payment-transactions-service.ts:478`). Add a chef action-required receipt with safe retry link and verified state; decide whether M needs email. This is a missing initial failure notice, not a claim that no financial-failure emails exist.

7. **Storage end/expiry-warning template has no active email trigger.** Defined generator is unused; API provides warning data only (`server/email.ts:4692`, `server/routes/bookings.ts:259`). Current storage reminder plan is arrival (`server/services/advance-reminders.ts:123`). If product policy requires a removal/end reminder, add a durable end/removal plan; do not reactivate a template that conflates estimated overstay and approved charges. Check-in-open and some chef assistance receipts are intentionally in-app-only (`server/services/advance-reminders.ts:236`, `server/services/visit-assistance.ts:65`); these are policy decisions to review, not conclusively misplaced email.

8. **Uneven durability and retry duplication.** Booking outbox sends SMTP then marks delivered (`server/services/booking-lifecycle-delivery.ts:185`, `server/services/booking-lifecycle-delivery.ts:187`); outcome worker explicitly acknowledges accepted-before-recorded resend uncertainty (`server/services/outcome-delivery.ts:52`). Tours persist sending-attempt evidence before SMTP and route ambiguous attempts to review (`server/services/tour-delivery-service.ts:846`, `server/services/tour-delivery-service.ts:850`). Legacy direct/fire-and-forget sends and Date.now tracking have weaker recovery (`server/routes/bookings.ts:451`, `server/services/overstay-penalty-service.ts:2033`); legacy route/webhook chef request uses same tracking ID but only short in-process dedupe (`server/routes/bookings.ts:3608`, `server/routes/webhooks.ts:1182`, `server/email.ts:221`). Persist intent and pre-send attempt ownership; avoid blindly retrying uncertain acceptance. Separate claim/penalty charged template + outcome emails are overlapping contracts to consolidate, not proof of identical duplicate sends (`server/routes/webhooks.ts:2991`, `server/routes/webhooks.ts:3270`, `server/services/outcome-delivery.ts:29`, `server/services/outcome-delivery.ts:266`).
