# Phase 0: copy, terminology and service-fee audit

Audited 2026-10-11, `development` at `1417751f`, including the existing working tree. Requested read-only review: no source, configuration, database, provider, email or deployment changes. The only intended new repository artifact is this report. Evidence pack read first: `docs/architecture/phase0/phase0-evidence-pack.md`; companion timezone/email report read next. Evidence below is repository-relative **file:line**, against the working tree inspected, not a claim about deployed code. The existing modification to `server/services/stripe-checkout-service.ts` was inspected as found.

Audience `chef` below is the existing technical customer role, **not proposed customer-facing terminology**. `all` means the same copy reaches customer, manager and sometimes staff. Proposed `{name}`, `{firstName}`, `{kitchen}`, `{amount}`, `{date}`, `{time}` and `{reference}` are presentation inputs, not literal copy. When a name is unavailable, use “Hi,” for greetings and “the customer” / “the person who booked” in manager explanations. Do not guess a name from an email address.

Scope: keyword searches across `client/src`, `server`, `shared`; inspected booking checkout, decisions, cancellation/refund, change requests, attendance/history, linked equipment/storage, extension, claims/overstays, notification producers, email templates, receipt/PDF and fee computation paths. English copy is the editorial baseline. French/Ukrainian fee-label counterparts were located; full translation quality and legal-document accuracy were not audited. Tests/generated search content/CSS numeric matches are excluded from copy findings. Existing graph queried for navigation, then every cited claim checked in source. No graph rebuild or child-agent work.

## A. Biggest problems

1. **The active confirmation path deliberately discards recipients’ names.** It selects only IDs/email/role (`server/services/booking-lifecycle-delivery.ts:25`) and supplies `Chef`, `Manager` or `Local Cooks` as the greeting name (`:83`), so the template’s `Hi ${firstName}` (`server/email.ts:3924`) produces “Hi Chef”. Resolve each recipient’s real name; separately resolve the booking customer’s name for manager messages. Existing resolver is reusable but its `A chef` and email-local-part fallbacks need presentation-safe handling (`server/utils/user-display.ts:10`, `:14`, `:68`, `:71`). Several legacy/extension routes pass email addresses as names (`server/routes/bookings.ts:2618`, `server/routes/webhooks.ts:1705`, `server/routes/manager.ts:6872`).

2. **Internal financial/workflow language is the actual end-user message.** Request copy says “authorized and has not been captured” (`server/services/booking-checkout-fulfillment.ts:87`); cancellation says “recorded manager-share refund quote” and “admin approval” (`server/services/booking-cancellation-refund.ts:179`); the shared review shows “Payment source #”, “Captured”, “Customer refund / manager debit” and provider IDs (`client/src/components/booking/CancellationRefundReview.tsx:39`, `:40`, `:42`, `:48`). These are sent to both audiences by the shared lifecycle queue (`server/services/booking-lifecycle-delivery.ts:70`, `:78`, `:151`). Preserve the precise financial state internally; present what happened, the amount, next action and whether the reservation is still held.

3. **Zero-fee pilots are not supported consistently by presentation.** Stripe itemized checkout and primary receipt rows already hide zero (`server/services/stripe-checkout-service.ts:224`, `:477`; `client/src/components/booking/BookingPricingBreakdown.tsx:69`). The tax popover still prints the zero fee whenever kitchen tax is positive (`client/src/components/booking/BookingPriceSummary.tsx:56`, `:109`), confirmation emails always print it (`server/services/booking-lifecycle-delivery.ts:65`), change UI/events always print it (`client/src/components/booking/KitchenBookingChanges.tsx:25`, `:29`; `server/services/kitchen-booking-changes.ts:194`), and refund review always prints a fee-review row/explanation (`client/src/components/booking/CancellationRefundReview.tsx:45`, `:56`). Static cancellation policy text also mentions fees regardless of the recorded amount (`shared/kitchen-booking-policies.ts:12`). Hiding just the checkout line does not meet the owner’s rule.

4. **The configured rate is real, but defaults and historical calculations disagree.** Primary configuration is `platform_settings.platform_commission_rate`, parsed with zero preserved (`server/services/stripe-checkout-fee-service.ts:103`, `:117`) and updated by staff (`server/routes/admin.ts:2380`). Its default is 0 (`server/services/stripe-checkout-fee-service.ts:74`). The pricing wrapper’s exceptional fallback and standalone helper default are 5% (`server/services/pricing-service.ts:157`, `:167`), as is the payout statement’s unused initialized rate (`server/services/payout-statement-service.ts:28`). No executable booking-fee constant of 7%/0.07 was found in the scoped non-test source; those matches are comments/examples (`server/services/stripe-checkout-fee-service.ts:369`, `client/src/lib/booking-price-estimate.ts:10`, `:26`, `client/src/pages/BookingDetailsPage.tsx:69`). Do not mistake this for verification that the live database is at 0%.

5. **Platform fee HST is not wired into the booking money/document contract.** The comment that Local Cooks is not registered contradicts the owner’s confirmed fact (`shared/booking-pricing-breakdown.ts:11`, `:20`). The shared helper can compute platform-fee HST, defaulting to zero when omitted (`:214`, `:231`), and the UI has a conditional line (`client/src/components/booking/BookingPricingBreakdown.tsx:76`). No booking caller supplying `platformHstRatePercent` was found. Checkout/capture currently reconcile subtotal + kitchen tax + fee only (`shared/booking-capture-terms.ts:22`; `server/routes/bookings.ts:3281`; `server/services/invoice-service.ts:354`). Receipts/PDFs need separate supplier identity, Local Cooks GST/HST number and a platform-fee tax line when relevant. **This requires a money-contract change, not merely inserting a line in a PDF.** No platform GST/HST number field/render was found in the inspected schema/invoice/statement sources. No rate, registration number or legal conclusion is invented here.

6. **Some wording promises a financial result or state that has not happened.** Extension authorization emails say “Amount Paid” (`server/email.ts:4526`; authorized state at `server/routes/webhooks.ts:1529`); storage cancellation requests call a “Booking Cancelled” generator (`server/routes/bookings.ts:463`, `:479`; `server/email.ts:4008`). Notifications unconditionally promise refunds after extension rejection (`server/services/notification.service.ts:1034`). Name/copy edits must keep hold, charge, cancellation acceptance and refund completion separate. Never turn “refund not yet verified” into “refunded”.

7. **Tax ownership and brand are unclear.** “Taxes & non-govt. fees” merges kitchen tax and company revenue (`shared/i18n/locales/en-CA/booking.json:226`; fallback at `client/src/components/booking/KitchenBookingFlow.tsx:2035`). Terms say Local Cooks does not collect HST on owners’ behalf and owners invoice separately (`client/src/components/legal/TermsContent.tsx:736`, `:740`), while checkout charges kitchen tax and passes kitchen gross to the manager (`server/routes/bookings.ts:3281`; `server/services/manager-payout-math.ts:6`). Explain collection through checkout versus remittance responsibility precisely. Company-as-“admin” remains in refund/overstay surfaces; “LocalCooks” remains in notifications/onboarding. Internal staff labels may remain.

Current-tree correction to the evidence pack: manager list `cancellation_requested` is already mapped to `cancelRequested` (`client/src/components/manager/bookings/columns.tsx:765`, `:769`); customer list maps it too (`client/src/components/booking/ChefBookingsView.tsx:350`, `:353`, `:994`, `:997`). Booking **detail** still falls through to the raw status (`client/src/pages/BookingDetailsPage.tsx:530`). Do not blindly replace every enum identifier.

**Change-feature reachability:** new confirmed-booking preview/request/checkout are explicitly rejected (`server/services/kitchen-booking-changes.ts:247`, `:261`, `:422`). The detail page still renders historical requests and `ChangePrice` (`client/src/pages/BookingDetailsPage.tsx:1339`; `client/src/components/booking/KitchenBookingChanges.tsx:80`). Thus their unconditional zero-fee text is a historical-record defect; the leftover new-change dialog/quote arithmetic is not an available new-booking workflow. Remove misleading retired UI or explain current limits; do not re-enable the feature as part of copy work.

## C. Shared glossary and voice guide for implementers

### People and brand

- **Platform:** “Local Cooks”; “we” when speaking as the platform. Avoid “LocalCooks”, “admin”, “Local Cooks admin” and “the platform” in transactional explanations. Keep URLs, email addresses, product IDs, enum values and DB fields unchanged.
- **Booking customer:** actual name in manager-facing titles/actions and a verified first/preferred name in greetings. Customer-facing copy normally says “you”/“your”. Examples: “Hi Priya,”; “Priya requested a booking”; “Message Priya”. Avoid “Hi Chef”, “Dear Chef”, “the chef”, “Chef message”, “chef’s card”. Missing name: “Hi,” and “the customer”; never an email local part masquerading as a name.
- **Kitchen manager:** name when known; “the kitchen manager” for their responsibility. A business’s kitchen/listing name can identify the host organization. Do not imply that every manager owns the building.
- **Staff:** “staff”, “Local Cooks team”, “Local Cooks review”. “Admin” is acceptable only for an explicitly staff-user role/control on an internal dashboard. Author labels in participant history say “Local Cooks”.
- **Tours:** “visitor” as the generic noun, actual name for a particular person. “Booked by” for financial/booking person columns; “Visitor” for tour columns.

### Bookings and payments

- “Booking request”, “Awaiting kitchen manager approval”, “Booking confirmed”, “Cancellation requested”, “Booking cancelled”, “Booking completed”. Never raw `cancellation_requested`; never describe a request as cancelled/confirmed before the corresponding decision commits.
- “Card hold”, “Amount held”, “Card hold released”, “Amount charged”, “Payment received”, “Refund requested”, “Refund being checked”, “Refund sent”, “Partial refund”. Avoid “authorized”, “captured”, “voided”, “reconciliation”, “recovery”, “source”, “ledger”, “manager debit”, “provider outcome”, “frozen allocation” in participant copy.
- Customer hold example: “We’ve placed a hold on your card. You’ll only be charged for items the kitchen manager accepts.” Manager example: “{name} requested this booking. Review the items to accept or decline them.” When no future charge is possible, state “You weren’t charged” only after verified hold release/no charge.
- Refund success example: “A refund of {amount} CAD has been sent to your original payment method. Your bank may take time to post it.” Pending/uncertain example: “We’re checking your refund. Please don’t submit another payment or refund while we review it.” No unsupported guaranteed bank-arrival date.
- “Kitchen price”, “Equipment”, “Storage”, “Subtotal”, “Kitchen HST”, **positive-only** “Local Cooks service fee”, **positive-only** “HST on Local Cooks service fee”, “Total”, “Estimated payout”, “Net payout”. Avoid merged “Taxes & non-govt. fees”, generic “platform fee” and “commission” on participant financial surfaces.
- **Payment processing cost is distinct from the Local Cooks service fee.** Zero service fee does not mean zero processing costs, free bookings or guaranteed full refunds after confirmation. Explain any retained processing cost only when the agreed policy and verified quote support it.
- **Kitchen HST:** set per kitchen by the manager, passed through to the kitchen business. Customer copy: “Kitchen HST ({percent}%)”. Manager copy: “Kitchen HST included in your payout”. Do not imply Local Cooks remits kitchen tax. **Local Cooks fee HST:** separate tax attributable to Local Cooks’ own service, with its own supplier/registration identity.
- Use a public booking reference and item/listing names. Provider IDs and transaction primary keys belong in staff diagnostics, not subject lines or primary prose.
- “Newfoundland time” with date-appropriate “NST” or “NDT” for scheduled times/deadlines. IANA IDs belong in storage/configuration, not email prose. Do not relabel an instant without formatting it correctly.

### Voice and truth

1. Lead with what happened, then what happens next and one primary action. Use short, calm sentences and sentence case. Avoid celebration/warning emoji, needless exclamation marks, “day(s)”, “non-govt.” and unsupported threats.
2. Render role-specific copy from the same verified event facts. The customer needs their charge/refund and reservation state; the manager needs {name}, the decision, tax in their payout and their own refund deduction. Neither needs a database procedure explained.
3. Say “We’re checking…” for a real uncertain state; do not turn it into a confirmed success to sound reassuring. Keep “don’t pay/refund again” when needed to avoid duplicate money movement.
4. Humanize expected errors with a concrete next action. Keep detailed provider/SQL/HTTP information in logs. Unknown statuses use a safe label and support link. Do not just replace underscores with spaces.
5. Use shared localization keys for recurring phrases, names and state labels. English, French and Ukrainian use the same display conditions. Localized text, fallback strings, tooltips, accessible labels, SEO metadata, PDF text and persisted email/notification bodies are all user-facing copy.
6. Owner terminology decisions supersede the stale “not registered” source comment. Copy cannot fix an absent tax calculation or decide refund policy. Confirm those financial contracts before changing a charge/refund promise.

### D5. Single display rule and central enforcement proposal

**Rule:** For the relevant quote, payment or booking, show any Local Cooks service-fee content **only when its authoritative fee amount in cents is greater than zero**. This gates the amount row, percentage, tooltip trigger/content, aria text, marketing badge, retained-fee sentence, fee-tax row, and refund-review/action. For a new quote derive the amount from the current configured rate and quote subtotal; for a historical receipt use its saved actual fee. Never gate a historical receipt on today’s platform rate. Do not round an unknown amount into zero: an incomplete quote says “Final price unavailable”, and does not invent a fee.

Keep numeric zero in internal APIs/DB/audit records; omission is a **presentation** rule, not destruction of evidence. The refund-review action additionally requires a positive **remaining refundable fee**, and the change UI distinguishes the positive **new fee** from the positive **original retained fee**. Kitchen HST remains independently visible when positive. A fee-free pilot still has kitchen prices, possibly kitchen HST and actual processing costs.

Enforce centrally in these existing seams, with no new parallel pricing system:

1. **Financial presentation data:** extend `shared/booking-pricing-breakdown.ts:208` (receipt builder) and its payout builder at `:261` to expose fee visibility and optional fee/tax presentation lines from authoritative cents; share the same rule for quote/refund/change presentation. Quote calculators at `client/src/lib/booking-price-estimate.ts:46` and `server/services/stripe-checkout-fee-service.ts:311` supply amounts, not strings. Display-rate helper at `client/src/lib/booking-price-estimate.ts:32` must not create a fee label for zero.
2. **UI:** existing `client/src/components/booking/BookingPricingBreakdown.tsx:69` / `:139` are good guards to reuse. Apply the shared predicate to `client/src/components/booking/BookingPriceSummary.tsx:56`, `KitchenBookingChanges.tsx:25`, `CancellationRefundReview.tsx:45`, policy/helper strings and their tooltip/accessibility content. Ensure positive-fee explanations are conditional at the caller, rather than a popover that independently guesses rate.
3. **Email/in-app:** `server/services/booking-lifecycle-delivery.ts:19` owns common booking communications. Queue presentation facts with saved fee and named participants, then render recipient-specific text through shared email layout instead of static strings from producers. Apply conditional lines in the producer/renderer boundary for confirmation at `:65`, cancellation at `server/services/booking-cancellation-refund.ts:179`, changes at `server/services/kitchen-booking-changes.ts:194`, and shared policy renderers. 4. **Stripe:** keep positive-line guards at `server/services/stripe-checkout-service.ts:224` and `:477`. Generate tax/fee line names from the same presentation facts as UI. Merchant receipt configuration is external and unverified; audit it before declaring total coverage.
