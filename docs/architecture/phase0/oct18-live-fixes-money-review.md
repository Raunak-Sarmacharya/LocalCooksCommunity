## Verdict

## Ranked findings

### M1 (Must): a price-down apply can replace kept-day subtotal cents with a different subtotal/tax split

`server/services/dated-booking-changes.ts:224-226,243-248,386-400,403-410` (quote and refund-part split); `:209-215` (the next quote trusts moved subtotal cents).

- **Problem:** the quote determines exact new kitchen, tax and service-fee totals. The refund plan saves gross money and platform return, but the mover reconstructs its refunded tax/subtotal using the **old source ratio**: `roundRatio(gross, tax, sub + tax)`. It then spreads whatever subtotal remains. It never asserts that the new live component subtotal/tax totals equal `quote.newTerms`. Preserving a future kept day from this ledger freezes the reconstruction error as its new price. This is not an incorrect gross Stripe refund or a failure of captured-source conservation.
- **Scenario A, unchanged settings (cents):** a valid offered three-day kitchen subtotal **54001** splits **18001 / 18000 / 18000**, with aggregate HST **8100**, service fee **3780**, captured **65881**, actual card fee **1941**. Keep Monday and Wednesday, drop Friday, and add a **9**-cent item on Monday. Approved new terms are kitchen/equipment **36010**, tax **5402**, fee **2521**. Apply succeeds, but live destination parts contain **36011 / 5401 / 2521**. Monday's kitchen part becomes **18002**, despite quote and original price **18001**. Totals still equal **43933**.
- **Scenario B, changed tax setting (cents):** standard **65880** booking, three **18000** days. Kitchen tax changes from 15% to 10%; keep Monday/Wednesday and drop Friday. Quote says **36000 + 3600 + 2520 = 42120**, refund **23060**, card fee kept **700**. Apply succeeds with live kitchen subtotal **34435**, tax **5165**, fee **2520**. The parent and visit price snapshots still advertise the quoted **36000** subtotal. The next quote reads the two kept kitchen prices as **17218 / 17217**, rather than **18000 / 18000**. A **1565**-cent subtotal discrepancy has become future pricing input.
- **Proof:** tests named `proof M1: a tax change...` and `proof M1 rounding...` in the new test file. They execute preview/request/approval/refund reconciliation and inspect actual live allocation rows; the first also previews another change.
- **Smallest safe fix:** before any provider refund, freeze the exact subtotal/tax/service reductions for each source and require their aggregate residual to equal the destination quote. Use those frozen reductions when writing the settled refund part. Fail closed before money moves if the source splits cannot fund that exact result. An after-money assertion alone would only send an already-refunded booking to recovery; changing `paidFor` to trust the visit snapshot alone would hide the wrong ledger split.

### M2 (Must): independently rounding moved sources changes unchanged day prices on a subsequent change

`server/services/dated-booking-changes.ts:379-403` (`moveLedger` runs `allocateCents(sub, weights)` separately for every source); `:209-219` (kept prices sum those allocations).

- **Problem:** preserving every source total does not preserve every destination component total. Separate largest-remainder allocations can award their rounding cents to the same component. The positive charge's `increases` allocation is correct in this scenario; the error is moving the earlier payments independently over their common residual weights.
- **Scenario (cents):** start Monday/Wednesday/Friday at **18000** each. First change adds only a Wednesday mixer, **2500**, paid through a separate **3050** charge. That charge correctly belongs only to Wednesday. Second change retains all three days/mixer and adds Saturday at the new **20000** rate, charge **24400**. The second approved quote keeps **18000 / 18000 / 18000**. The old **54000** source moves as kitchen subtotals **17204 / 17204 / 17203**, mixer **2389**. The old **2500** supplemental source moves as **797 / 796 / 796**, mixer **111**. Combined kept kitchen prices become **18001 / 18000 / 17999**. Saturday remains **20000**. Every source still conserves its capture and fee. Another preview now preserves the altered prices, not the approved/original ones.
- **Proof:** `moves two sources conservatively on a second change...`. It makes both changes through the real engine, synchronizes CP5, asserts source paid/fee conservation, asserts the **18001 / 18000 / 17999** live result against the saved quote's **18000 / 18000 / 18000**, and checks that another preview reads the altered result. Replaying CP5 does not repair it or restore an old manifest.
- **Smallest safe fix:** allocate the remaining source rows against a **shared per-component residual budget**, subtracting each row's assigned subtotal before allocating the next, and let the final source fill the exact remainder. Validate source sums and destination component sums, including zero/new components, before capture/refund. Preserve unchanged paid components directly when possible. Apply the same reconciliation principle to the other split columns; do not independently round a complete destination target for every source.

### S1 (Should): a disabled current rate blocks preserving an already-paid day

`server/services/dated-booking-changes.ts:205-219`; `server/services/dated-booking-quote.ts:44-45`.

- **Problem:** `priceBookingDays` validates/prices **all** destination days at today's rates before the kept-day override. A zero/null current daily rate throws before the paid **18000** can be restored.
- **Scenario (cents):** three paid full days at **18000**, current daily rate becomes **0** because the kitchen stops selling new full days. Keep those exact days and add Saturday for four hourly slots at **2250**: the only new kitchen amount should be **9000**. Preview instead returns `contactKitchen`, even though none of the new time needs a daily rate. No wrong charge occurs; this fails closed and requires support.
- **Proof:** `proof S1: removing the current daily offering...`.
- **Smallest fix:** identify kept days/components first and price only new/changed components with current rates. Continue validating inventory and equipment eligibility. Require a current nonzero daily rate only when actually buying a new/changed daily day.

## Verified OK

1. **The intended first-change price preservation works.** After list daily pricing rises to **20000**, three untouched **18000** days plus Saturday total kitchen **74000**, tax **11100**, fee **5180**, charge **24400**. Actual approval keeps the quote. The extra charge has component subtotals **[0,0,0,20000]**. Captured-source totals and actual fee shares conserve after CP5 synchronization. Exceptions on later moves/negative splits are M1/M2.
2. **Quote integrity and consent.** Preview hash changes when a newly purchased day's list price changes; submitting the stale hash refuses `priceChanged`. Request rebuilds the quote. A subsequent listing increase after the request does not silently change the saved approved amount; approval applies the saved quote and captures once. `datedChangeFingerprint` includes the individual preserved kitchen/equipment amounts (`dated-booking-changes.ts:262-266`). `detailedPreview` in the proof file checks the public money projection against the real internal price result; public preview intentionally omits internal `datedDays/newTerms`.
3. **No low-price carry through a changed identity.** Same date but daily-to-hourly change uses current hourly prices; a different date uses current daily prices; changing an hourly interval uses current hourly prices. A reordered input day list normalizes to the same quote/hash. Kept matching requires date, mode and the whole normalized slot sequence, not just duration. Re-adding an actually CP6-dropped Friday uses **20000**, not its old **18000**. Approval of that re-add leaves the earlier settled allocation/refund unchanged and live new day subtotals are **18000 / 18000 / 20000**.
4. **Equipment is matched by paid booking row, not listing price alone.** An existing Monday mixer keeps **2500** after list price becomes **4000**; a new Wednesday mixer costs **4000**. Removing Monday's paid mixer with all days retained quotes refund **2961**, fee kept **89**, and leaves three **18000** kitchen parts. Earlier removed/refunded equipment stays settled with zero kitchen entitlement; re-adding it charges **4000** (gross **4880**) entirely on that item's new component, with no second old refund. Source totals/fees still balance.
5. **Partial/extra/outside refunds fail closed.** Existing active-part refund records or a kitchen debit refuse `datedChangeSupport`. A real CP6 **1000**-cent extra day refund is reconciled to succeeded first, then the change refuses. An unallocated outside refund also refuses. No kept-day override restores that refunded entitlement.
6. **Invitation prices and Checkout card storage.** The actual session builder requests `customer_creation: 'always'`, manual capture, and `setup_future_usage: 'off_session'`, without destination/application-fee routing (`stripe-checkout-service.ts:85-86`). Real dated fulfillment persists customer and payment-method ids from both string and expanded-object provider references (`dated-booking-fulfillment.ts:116-117`). Tests cover normal checkout and a **54000** invited kitchen subtotal versus **60000** list subtotal, with **2500** equipment per day. Real invitation acceptance captures the fake provider once; replay reuses the booking/source and captures nothing again. A later change still prices invited kept days at **18000** and their equipment at **2500**, after listings rise to **30000 / 6000**. The new day uses **30000**.
7. **Current-day extension reads cannot silently redirect writes.** Day 2 is picked in session, before arrival, and after its late departure (`session-extensions.ts:225-236,269`). Creating without a visit still throws; sending day 1's stale visit with day 2's boundary refuses. The offer saves day 2 explicitly. The client sends `state.visitId` for chef requests and manager early/extension/overstay actions (`SessionExtensionRequest.tsx:78`; `SessionExtensionsCard.tsx:321,335`). Reconciliation/application choose the extension's persisted visit (`session-extensions.ts:212,553,573`).
8. **Extension prices stay per visit at the frozen rate.** Booking extra-time snapshot **2500** wins over a current kitchen rate **9000**. A 60-minute day-2 offer is **3050**; 30-minute early start is **1526**; a recorded **40**-minute overstay rounds to **60** billable minutes, **3050**, rather than using the whole multi-day duration. A second overstay charge for that visit refuses. The early/offer/overstay proof records the offer; it does not simulate every later payment decision.
9. **Payout fallback is display-only.** An authorized per-day source with no day rows displays estimated **62100**, then calling release leaves the source unchanged and creates no installment. `releaseKitchenPayout` dispatches per-day sources to day release regardless of missing rows (`kitchen-payout-service.ts:167-169`); its inner legacy release also refuses (`:99`). No booking-level transfer from the estimate was found.
10. **The new chef day-money projection contains no kitchen-private share.** Route ownership checks precede the read (`server/routes/bookings.ts:708-724`); the new projection strips `kitchenRemainingCents` (`:1012-1013`). The actual day-money reader plus that exact projection yields only visit id, paid **21960**, refunded **0** (and optional pending refund cents); it does not expose **20053** kitchen entitlement, provider fees, source ids or receipt metadata. This test is of the reader/projection, not an HTTP route integration test.
11. **Lifecycle fixes do not edit a capture/decision path.** `66352b57` only changes the two notice/reminder start reads to `bookingFirstStart` (`manager-decision-reminders.ts:30`; `auth-expiry-service.ts:237`), using the sorted frozen dated policy. `5f2db9ea` supplies already-loaded visits to the confirmation deadline helper (`booking-lifecycle-delivery.ts:219`).
