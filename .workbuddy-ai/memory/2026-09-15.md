# 2026-09-15

## Email verification loop — rebuilt around "email is the primary identifier"

Rebuilt the auth verification flow so an unverified **email** blocks every mutating
action platform-wide, while an unverified **phone** blocks nothing. Approved the
gate modal and profile card designs with the user before writing code.

### Root causes found (the symptoms were misleading)
1. **Blank email field** — the `users` table has no `email` column; the registration
   address lives in `users.username`. `ManagerProfileSettings.tsx` read
   `user.email || firebaseUser?.email`, both null for a phone-first account.
   `ManagerProfile.tsx` / `ChefProfileSettings.tsx` already patched this with a
   `user.username` fallback; the dashboard one did not.
2. **Dead "Verify email" button** — the branded link came from Firebase Admin's
   `generateEmailVerificationLink(email)`, which **requires the email to already be
   on a Firebase user**. A phone-only account has none, so it threw
   `auth/user-not-found` → 404 → "No account found for this email."
3. **Silent registration failure** — `EnhancedRegisterForm` called
   `verifyBeforeUpdateEmail` as a best-effort follow-up; it needs a *recent
   sign-in*, which a fresh phone signup usually lacks. Removed.
4. **Login loop** — `ProtectedRoute` redirected unverified users to `/auth`, so they
   could never reach the profile page that fixes it.
5. **Split-brain risk** — `users.username` is `NOT NULL UNIQUE` and *is* the email,
   so an email change has to rewrite it atomically.

### What was built
- **Server-owned token loop** (`server/routes/user-email-verification.ts`,
  `server/email-verification.ts`): `/api/user/email/verification/{start,resend via
  start,cancel,confirm,preview,status}`. SHA-256 token digest only; raw token exists
  solely in the emailed link. `confirm` is public (the token is the proof) and calls
  Firebase Admin `updateUser(uid, { email, emailVerified: true })` **then** rewrites
  Neon, with a Firebase rollback if the DB write is rejected.
- **Migration** `0034_add_email_verification_flow.sql`: `pending_email`,
  `pending_email_token_hash`, `pending_email_expires_at`, `pending_email_sent_at`,
  `email_verified_at` + partial index. Backfills `email_verified_at` for verified rows.
- **Gate** — `requiresEmailVerification()` (`client/src/lib/auth-verification.ts`) is
  the single client predicate; `hasVerifiedEmailClaim()` is the server one. Applied in
  `requireFirebaseAuthWithUser`, `requireManager`, `requireChef`; admins exempt.
  `CONTACT_VERIFICATION_REQUIRED` → `EMAIL_VERIFICATION_REQUIRED`.
- **UI** — `EmailVerificationCard` (4 states: needs-address / unverified-idle /
  unverified-sent / verified / verified-changing) and `EmailVerificationGate`
  (non-dismissible; Verify / Sign out / Contact support). Both read the same
  react-query key so opening the gate costs no extra request.
- **`useEmailVerificationGuard`** — guards tour + booking submits so the user gets the
  gate instead of a bare 403. Buttons stay *enabled* on purpose.
- **Getting started** — manager row and chef row now track email **verification**
  (not presence) and deep-link to `?focus=email`.
- **Security fix** — `GET /api/user/profile` was spreading the whole row, leaking the
  password hash. Now strips `password` and `pendingEmailTokenHash`.

### Gotchas worth remembering
- **Firebase caches `email_verified` in the ID token for up to an hour.** Confirming on
  another device stays invisible until the token refreshes, so
  `fetchEmailVerificationStatus()` forces `reload()` + `getIdToken(true)` first.
- `AuthModalProvider` and `ScheduleViewingWidget` each had their own `isUserVerified`
  with **different** semantics (email-AND-phone vs email-OR-db). Both reconciled to
  match the server. A client stricter than the server strands users on a wall the API
  would have let through.
- `/email-verify` (new, branded) is separate from `/email-action` (Firebase oobCode,
  still used by email/password signup). Deliberate: `EmailAction.tsx` is 54 KB and
  handles password reset + email recovery; adding a branch risked destabilising it.
- `AlertDialog` can't be made non-dismissible with rich content — used `Dialog` with
  `showCloseButton={false}` + prevented `onEscapeKeyDown`/`onPointerDownOutside`.

## Follow-up fixes (same day, after user testing)

### The verification link pointed at a route that does not exist
I had invented `/email-verify`. The canonical landing page — used by every existing
verification email and the magic-link flow — is **`/email-action`**. Link is now
`${getEmailLinkOrigin(userType)}/email-action?mode=verifyEmail&token=…`, matching the
Firebase action-code shape. Deleted `pages/EmailVerify.tsx`, removed the `/email-verify`
route, dropped the now-unused `/preview` endpoint + `confirmEmailVerification` /
`previewEmailVerification` / `readVerificationToken` client helpers.

`EmailAction.tsx` now branches on a `token` param *before* the `!oobCode` guard. The
`return` in that branch is load-bearing: it is what narrows `oobCode` to `string` for
every Firebase-driven mode below, so removing it reintroduces five TS2345 errors.

### Gate button was wrong for auto-sent links
Phone-first signups get the link automatically, so "Verify email now" (which navigated
away to the profile) was the wrong primary action. It is now
**"I have verified my email"** → `refreshUserData()` (reload + forced token refresh,
because `email_verified` is cached in the ID token). On failure it shows an inline
"we have not detected it yet" alert. The profile is still reachable via a
"Resend or change email" text link, so the resend/change escape hatch is preserved.

### Manager sent straight to onboarding, sidebar checklist gone
Regression I introduced. `ManagerProtectedRoute`'s locations query was gated on
`hasCompleteContactVerification` (email **AND** phone). A Google-registered manager has
no Firebase phone, so the query stayed disabled → `managerLocations` was `undefined` →
`Array.isArray(undefined)` false → the onboarding redirect never fired. Relaxing that to
email-only enabled the query, returned `[]` for a new manager, and fired
`<Redirect to="/manager/setup" />` — a full-screen wizard with no sidebar, which is why
the "Getting started" popover disappeared too.

Fix: `needsOnboarding` now also requires `!emailUnverified` (every onboarding save is
refused server-side while unverified, so the wizard could never complete), and the
locations query is `enabled` only when the email is verified so it does not fire a
guaranteed 403.

### Catalog hygiene
My earlier append scripts had left standalone `,` lines in `auth.json`, so the files were
one edit away from invalid JSON. Re-serialised all three (JSON round-trip, whitespace
only — the diff stays confined to the appended keys) and pruned 14 keys orphaned by the
route merge. All three locales at 225 keys, parity intact, lint still shows only the 7
pre-existing failures.

## Round 3 — link origin + post-verification destination

### "Invalid email action link" on the emailed link
Reproduced from the user's screenshot: the link pointed at
`https://dev-chef.localcooks.ca/email-action?mode=verifyEmail&token=…` and the page
answered "Invalid email action link" — the `!oobCode` guard firing, i.e. the token
branch was absent. **Root cause: that host serves the deployed bundle, which predates
the token handling.** The code is correct; the staging client needs deploying.

But the underlying design was still wrong: `getEmailLinkOrigin` *deliberately* resolves
to a public host even when the API runs locally ("so links work outside localhost"),
so a locally generated link lands on staging whose bundle may lag — a working link
presenting as broken. Added `resolveTrustedLinkOrigin(rawOrigin, role)`
(`server/email-verification.ts`): the client sends `window.location.origin` on
`/start`, and the server honours it **only** when it is a trusted host for that role:

- localhost family — `localhost`, `127.0.0.1`, `*.localhost`, **port preserved**
- production — `<role>.localcooks.ca`
- staging — `dev-<role>.localcooks.ca` (`BASE_DOMAIN` override respected)

Refuses: other roles' hosts, the bare domain, lookalikes (`chef.localcooks.ca.evil.com`),
non-default ports on public hosts, non-http protocols, non-strings, >200 chars. Falls
back to `getEmailLinkOrigin`. 15 tests cover the accept and refuse cases.

### Verification landed on a login page, not the dashboard
`DEFAULT_REDIRECT_PATHS` (the *verification* map) is:
`manager → /manager/login?verified=true`, `chef → /auth?verified=true`,
`admin → /admin/login?verified=true` — login pages. The user explicitly wants the
role dashboard. `POST_SIGNIN_REDIRECT_PATHS` already holds the right values
(`/manager/dashboard`, `/dashboard`, `/admin`), so both verification handlers now pass
`forSignIn = Boolean(auth.currentUser)`: signed-in users go to their dashboard,
signed-out users still get the login page (they have no session to land in).

Subdomain handling on the redirect was already correct and is unchanged —
`getSubdomainForRole` applies the `dev-` prefix on staging and preserves protocol/port
on localhost.

**Takeaway worth keeping:** when a locally-run API emails a link to a public host, the
bundle serving that host must already contain the code the link needs. Prefer honouring
the requesting origin (allow-listed) so the link opens against the code that made it.

## Round 4 — `emailVerifiedAt` mirror gap (completed after an interruption)

Adding `users.email_verified_at` left a gap: the six places that mirror Firebase's
`email_verified` into `is_verified` did not set it, so anyone who verified through the
**Firebase** path (email/password signup, or the middleware's stale-mirror repair) got
`emailVerifiedAt: null` — and the profile card rendered "This address is confirmed."
instead of "Verified <date>". Only our own token loop set it.

All six now write `emailVerifiedAt: user.emailVerifiedAt ?? new Date()`, which records
the first observation and never moves an existing date:

- `server/firebase-auth-middleware.ts` (stale-mirror repair)
- `server/routes/user.ts` × 4 (`GET /profile`, `POST /sync`,
  `sync-verification-status`, `verify-email-complete`)
- `server/routes.ts` (`firebase-sync-user`)

`?? new Date()` is safe because each site is guarded by `!user.isVerified`, and the
migration only backfilled rows where `is_verified = true` — so an unverified row has a
null date by construction.

## Round 5 — apply flow routed through the gate (task #8 closed)

Both apply paths now surface the gate instead of an opaque failure:

- **`AuthModalProvider`** — the guard in `submitPendingApplication` called
  `setSubmitError("Please verify your email first, then click Submit.")`. It now calls
  `openGate()`. The gate is rendered as a **sibling of the auth dialog**, not nested
  inside it: two stacked Radix dialogs fight over the focus trap.
- **`KitchenApplicationForm`** (`/apply-kitchen/:locationId`) — `onSubmit` is wrapped in
  `guard(...)` and the gate is rendered at the end of the tree. This path had no client
  check at all, so an unverified chef could fill the whole multi-step form and only be
  refused at submit. Added a **non-blocking** notice above the form (`blocked` from the
  hook) so they know up front, while the form stays usable — matching the "see
  everything, actions blocked" rule.

New `kitchen` namespace keys: `applyEmailUnverifiedTitle`, `applyEmailUnverifiedBody`.

**Catalog comma gotcha:** `auth.json` ends with a trailing comma but `kitchen.json` does
not, so the insert helper must branch on `head.endsWith(",")`. Wrapping the assembled
string in `JSON.parse` before writing is what caught it — keep doing that for any
scripted catalog edit.

## Round 6 — random logouts diagnosed (PRE-EXISTING, not from this work)

User reported being signed out on (a) manual refresh while the email is unverified and
(b) right after confirming from the verification link.

**Chain, fully traced:**

1. `use-auth.tsx:83` — `isInitializing` starts `useState(true)`, mirrored into
   `isInitializingRef`. So on **every page load** the first `onAuthStateChanged` callback
   sees `isInitializingRef.current === true`.
2. That makes `shouldSync` true (`use-auth.tsx:292`), so the client POSTs
   `/api/firebase-sync-user` — a request per page load.
3. `server/security.ts:341` puts `/api/firebase-sync-user` behind `authLimiter`, whose
   ceiling is `isProduction ? Math.min(config.authMaxRequests, 30) : config.authMaxRequests`.
   The `platform_settings` rows are all `999999` (limits "switched off"), but the
   `Math.min(..., 30)` cap **ignores that** — so staging/production allow **30 per 15 min
   per IP**.
4. Exceed it → **429**. `syncUserWithBackend` returns `false` for any non-OK response
   (`use-auth.tsx:198`).
5. `use-auth.tsx:353-358` — on `false` it does `await signOut(auth)` + `setUser(null)` +
   `authPhase='error'`. **The user is logged out.**

`git show HEAD:` confirms step 5 is in HEAD — pre-existing, not introduced here. The
verification work just adds page loads (the `/email-action` landing plus the redirect),
which is why it surfaced now.

**Also ruled out with evidence, do not re-investigate:**
- Migration 0034 **is** applied (all 5 columns + the index exist) — the schema change is
  not causing 500s.
- `/api/firebase-sync-user` and `/api/user/profile` are both in the recovery allow-list,
  so the new email gate does not 403 them.
- The DB has 13 users, all `is_verified = true` with a `firebase_uid`.

**Two distinct defects:** (1) a transient failure of a best-effort sync destroys a valid
session — only a definitive 404 should; (2) an idempotent, token-authenticated sync sits
on the *auth-attempt* limiter, whose budget exists for credential brute-forcing and is
meaningless here. Fixing only (1) stops the logouts; fixing (2) stops the 429s.

### Fix applied (user chose: keep the sign-out rule, fix the limit + the request volume)

1. **`server/security.ts`** — removed `app.use('/api/firebase-sync-user', authLimiter)`.
   There is no separate `apiLimiter`, so it now falls under the **global** limiter
   (300 / 15 min). It cannot be brute-forced: it requires a valid Firebase ID token and
   resolves the account from that token's uid.
2. **`client/src/hooks/use-auth.tsx`** — dropped `isInitializingRef.current` from
   `shouldSync`. That ref is true on every fresh load, which is what made this a
   per-page-load POST. Sync now fires only on `pendingSyncRef` (set by `login()`,
   `signup()`, and both Google paths — verified: lines 462/467/494/496/667/669/789) and
   on `isVerificationRedirect`.
3. **`client/src/pages/EmailAction.tsx`** — added `withVerifiedMarker()`, applied to the
   token-confirmation redirect. `isVerificationRedirect` requires a `verified` param, and
   the signed-in dashboard redirect (`POST_SIGNIN_REDIRECT_PATHS`) does not carry one, so
   without this the post-verification sync would silently stop happening.

Nothing was lost by dropping the per-load sync: the `is_verified` mirror is still repaired
by `/api/user/profile` and by `requireFirebaseAuthWithUser` on every authenticated request,
and the welcome email is sent by the verify-email-complete path and by our confirm endpoint.

**Residual risk the user accepted:** the `signOut(auth)` on sync failure is unchanged, so a
5xx or network blip on `/api/firebase-sync-user` still destroys the session. It is now much
less reachable (global limiter instead of a 30/15min auth budget), but not eliminated.

## Round 7 — verifying an email signed the user out (root cause PROVEN empirically)

**Any Firebase email change invalidates the account's refresh token.** Not a side effect of
using the Admin SDK — Firebase's own flow does it too. Measured with throwaway probe users
(created via Admin SDK, signed in over the Identity Toolkit REST API, then checking whether
the refresh token still works):

| Operation | Session afterwards |
|---|---|
| `adminAuth.updateUser(uid, { email })` | **dead** — `TOKEN_EXPIRED` |
| client `updateEmail(user, newEmail)` | blocked — `auth/operation-not-allowed` |
| native `generateVerifyAndChangeEmailLink` + `applyActionCode` | **dead** — `auth/user-token-expired` |
| …then `signInWithCustomToken(createCustomToken(uid))` | **restored, same uid** |

`auth/operation-not-allowed` on `updateEmail` means this project has **email enumeration
protection** on, so Firebase itself mandates verify-then-change. (The Admin SDK is exempt,
which is why our server-side change works.)

**Why it "didn't happen before":** two reasons, both real. Phone-first accounts never
successfully changed an email at all (the dead button from round 1), so there was no session
to lose. And the email/password flow uses `mode=verifyEmail`, which verifies the *current*
address — it never changes the email, so it never invalidates anything. The distinction that
matters is **verify ≠ change**.

**Why it logged out OTHER tabs:** the `/email-action` page called `updateUserVerification()`,
which does `getIdToken(true)`. That was the first thing to discover the dead refresh token,
and the SDK responds by signing out globally — propagating to the dashboard tab that was
showing the gate. So the ordering of the fix is load-bearing, not cosmetic.

**Fix (validated by probe):**
- `server/routes/user-email-verification.ts` — `/confirm` now reads an **optional** bearer
  token via `resolveCallerUid()`. When it matches the uid being confirmed, it mints
  `createCustomToken(uid)` and returns it as `sessionToken`. Requiring that proof is what
  keeps it safe: a link opened on an unrelated device (or by whoever owns a mistyped
  address) gets no token and simply is not signed in.
- `client/src/pages/EmailAction.tsx` — captures `getIdToken()` **before** confirming, sends
  it as the Authorization header, then `signInWithCustomToken(auth, sessionToken)` **before**
  `updateUserVerification()`. Restoring the session first means nothing ever forces a
  refresh against the dead token, so no global sign-out happens and other tabs keep working.

**Known limits to state plainly:** other tabs recover via Firebase's cross-tab sync; other
*devices* are signed out and must sign in again — unavoidable Firebase behaviour. If the
re-auth call fails, the address is still verified and the user just signs in normally.

### Reusable technique: proving Firebase Auth behaviour instead of guessing
`firebase-admin` + the Identity Toolkit REST API, no browser needed:
1. `adminAuth.createUser({ email, password, emailVerified })`.
2. Sign in: `POST https://identitytoolkit.googleapis.com/v1/accounts:signInWithPassword?key=<VITE_FIREBASE_API_KEY>` with `returnSecureToken: true` → gives a refresh token.
3. Refresh: `POST https://securetoken.googleapis.com/v1/token?key=<key>` with `grant_type=refresh_token`.
4. Perform the operation under test, then refresh again — a failure proves the session died.
5. Always `deleteUser` in a `finally`, and verify with `listUsers` that no `zz-probe*` strays remain.
For client-SDK behaviour, `initializeApp` + `getAuth` from `firebase/app`/`firebase/auth` work
in Node 22 (global fetch), and `user.getIdToken(true)` / `user.reload()` reveal a dead session.
